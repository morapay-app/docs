Failed v2 responses **do not** include `data`. They return an **`error`** object plus optional **`meta.request_id`**.

## Error envelope

```json
{
  "error": {
    "code": "request.validation_failed",
    "message": "Some fields are invalid.",
    "details": [
      {
        "field": "pay.amount",
        "code": "invalid_amount",
        "message": "Amount must be a decimal string."
      }
    ]
  },
  "meta": { "request_id": "req_1731810000000_a" }
}
```

| Field | Use |
|-------|-----|
| `error.code` | Branch in code; maps to docs under `/errors/codes/*` |
| `error.message` | Human-readable catalog sentence (safe to log) |
| `error.details` | Field-level validation issues when present |
| `meta.request_id` | Support correlation |

HTTP status reflects the error class (4xx client, 5xx server). Prefer handling **`error.code`** over status alone.

## Client pattern

```javascript
const payload = await res.json().catch(() => ({}));
if (!res.ok) {
  const code = payload?.error?.code ?? "unknown";
  const requestId = payload?.meta?.request_id;
  throw new Error(`${code} (${requestId ?? "no request_id"})`);
}
const { data } = payload;
```

## Rate limits

`429` responses use `error.code` `api.rate_limited`. Back off with jitter and honor `Retry-After` when present.
